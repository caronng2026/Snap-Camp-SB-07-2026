### Technical Decisions

| Date | Decision | Rationale |
|---|---|---|
| 2026-07-28 | v1 is a **browser-based web app, mobile-responsive** (OQ-2). Not a desktop app, not a native mobile app. | No install or app-store friction, so it can be put in front of the anchor partner fast for the "watch them use it" test. Keyboard-first SKU entry works naturally in a browser; a responsive layout also covers phone use on the shop floor. Native mobile was ruled out for v1 because the core interaction is fast repeated typing, which phone keyboards handle worst. An installable PWA is a later upgrade that needs no rework. |
| 2026-07-30 | The `frontend/` app uses **Vite with vanilla JavaScript modules and Vitest**. No UI framework. | Architecture Shaping Q1. The app is one screen, so a component framework buys little while adding dependencies and agent surface area. A light build step is required because the acceptance oracles for `UX02`–`UX05`, `SEC03`, `NFR01`, and `NFR03` specify integration tests; with no build step those would degrade to manual-only and the PRD's `failing_first` test strategy would need amending. Adds Node and npm as prerequisites. |
| 2026-07-30 | **One spreadsheet-writing dependency is approved in principle** for the `.xlsx` export. The coding agent selects the specific package against fixed criteria and reports the choice, licence, and bundle size for confirmation **before** writing code against it. | Architecture Shaping Q2. `OQ-10` makes a dependency effectively unavoidable: leading-zero SKUs survive only if cells are written as text, and hand-rolling OOXML would move Excel-compatibility risk onto us and make `NFR02` the hardest thing in the project. Criteria: (1) writes text-typed cells, (2) permissive licence (MIT or Apache-2.0), (3) actively maintained, (4) runs in-browser with no server, (5) smallest bundle satisfying 1–4. Package identity is deliberately not fixed here because registry, licence, and maintenance state must be verified at implementation time rather than assumed. |
| 2026-07-31 | **The export stays `.xlsx`** (OQ-12). `.csv` is not adopted. | Confirmed by the builder after the leading-zero reversal removed the original justification. The correctness argument no longer applies — SKUs are now stripped of leading zeros, so `.csv` would not corrupt them. The decision therefore rests on the remaining merits: `.xlsx` opens as a native Excel workbook with no import step, preserves column widths and formatting, and matches what the anchor partner already works in. **Cost accepted:** v1 carries one spreadsheet-writing dependency that `.csv` would not have needed. The five selection criteria recorded on 2026-07-30 still apply, and the agent must report the chosen package, licence, and bundle size before use. |
| 2026-07-31 | **SKUs are trimmed and upper-cased on entry.** `  ac4-100w ` is stored, displayed, and grouped as `AC4-100W`. Applied before the leading-zero rule, so normalisation order is: trim, upper-case, then strip leading zeros if the result is entirely digits. Inner spaces are preserved. This resolves the case-sensitivity and whitespace rules that `DATA-MODELS.md` had explicitly left **undefined** for v1. | Builder observed during `B005` manual verification that `ac4-100w` and `AC4-100w` consolidated as separate items and stated they are the same SKU. The `B005` stop condition for undefined grouping rules fired as designed and the work paused rather than inventing a rule. Whitespace was decided at the same time because it is the same class of problem and worse in practice: a trailing space is invisible on screen and would silently split a SKU, and pasting from an existing spreadsheet often carries stray spaces. Normalising once on entry follows the precedent set by the leading-zero decision, so storage, consolidation, and export need no case or whitespace logic of their own. **Accepted trade-off:** what the user sees differs from what they typed. Upper case was chosen over lower because item codes are conventionally upper case. |
| 2026-07-31 | **Leading zeros are stripped from purely numeric SKUs.** `00734` is stored, displayed, and grouped as `734`. A SKU that is not entirely digits is stored exactly as typed. `000` normalises to `0`. This **reverses the OQ-10 answer** recorded 2026-07-28. | Builder observed during `B002` manual verification that `00734` and `734` appeared as separate items and stated they are the same SKU. **Known risk, accepted:** if the anchor partner has two distinct items differing only by leading zeros, this silently merges them. No evidence either way was gathered; worth confirming with the client. **Consequence:** the justification for the `.xlsx` export decision was leading-zero preservation, and that justification no longer holds. OQ-3 must be revisited — see OQ-12. |
| 2026-07-30 | The daily log **rolls over automatically at local midnight**, and **prior days are retained indefinitely and never auto-deleted** (resolves OQ-6). | Architecture Shaping Q3. Satisfies `FR06` with no UI step and no action for the user to forget, which protects the speed bar in `UX01`. Automatic pruning was rejected: deleting user data is a destructive action the `PRD-001` risk model gates behind approval, and it would solve a storage problem that does not exist — ~200 entries per day keeps a full year well inside `localStorage`. **Accepted edge case:** work recorded after midnight lands on the next day's log. Judged acceptable for a specialty retail shop; revisit if a partner works past midnight. |
| 2026-07-28 | v1 persists data in **browser `localStorage`** (OQ-5). Not IndexedDB, not a user-managed file, not a backend database. | Survives reload and browser restart with no dependency, no server, and no setup, satisfying `PRD-001-NFR01`. IndexedDB solves a scale problem that ~200 entries/day does not have. A user-managed file would break the speed bar in `UX01`. A backend database would activate `backend/` and contradict `SEC03`, and is the v2 path. **Condition:** `localStorage` is per-device, per-browser, and can be wiped by clearing browsing data without warning. The daily `.xlsx` export (`FR05`) is therefore the **durable record** — the copy that leaves the browser. **Single-device use confirmed** by the client on 2026-07-28 (OQ-11), so `localStorage` is sufficient for v1 and the backend question stays closed for `PRD-001`. |
| 2026-07-28 | Application code lives in **`frontend/` and `backend/`, siblings to `precode/`** at the repository root (OQ-4). `backend/` stays absent and unbuilt until a backend bead is approved and activated; that absence is expected, not incomplete setup. | Establishes the directory convention once, so later work does not have to relocate code or rewrite path conventions. **Reaffirmed deliberately even though `PRD-001` v1 has no backend work**: `PRD-001` scopes a browser-only slice with no accounts, no external services, and no server (`SEC02`, `SEC03`), so `backend/` will stay empty through this PRD. The convention is recorded for scope beyond `PRD-001`, not for v1. This supersedes the agent's recommendation of a single neutral `app/` folder, which was argued on the basis that v1 alone needs no backend; the builder's decision weighs future scope over v1 minimalism. The principle that an app directory may be intentionally absent until an approved bead creates it is supported by `docs/PRECODE-SUPPORT-RUNBOOK.md:116`; the `frontend/`/`backend/` naming itself is a Snap Camp project decision, not a PrecodeOS convention. |
| 2026-07-28 | "Excel-ready" means a **`.xlsx` file download for v1** (OQ-3, revised by OQ-10). `.csv` is ruled out for v1. Clipboard copy is not the primary output. | The client confirmed the anchor partner's SKUs are **numeric with leading zeros** (OQ-10). Excel strips leading zeros from `.csv` on open, so `00734` would silently become `734` — a wrong item code in the file the product exists to produce. That is a correctness failure, not a formatting preference, and it would destroy trust in the export. `.xlsx` writes the SKU column as text and preserves the codes exactly. **Consequence:** v1 now requires a spreadsheet-writing dependency, which is an explicit approval gate in the `PRD-001` risk model and must be approved before the export bead. The original `.csv`-for-v1 decision is recorded as superseded below.  **Superseded rationale 2026-07-31:** leading zeros are now stripped, so the correctness argument for `.xlsx` no longer applies. The format choice is reopened as OQ-12. |
| 2026-07-28 | v1 remains **single-device** (OQ-11 confirmed). `localStorage` is sufficient and the `backend/` question stays closed for `PRD-001`. | The client confirmed the anchor partner records on one device only. The condition attached to the OQ-5 persistence decision therefore holds, and no backend or sync work enters v1. |

### Product Decisions

| Date | Decision | Rationale |
|---|---|---|
| 2026-08-04 | **The backend is Node with Fastify.** | Architecture Shaping Q1 under `B010`. One language across `frontend/` and `backend/`, so a single toolchain and mental model. Fastify over Express for active maintenance and first-class schema validation, which matters when every request carries values that must not be trusted. |
| 2026-08-04 | **Isolation is enforced by a space-scoped data-access layer.** Every data function takes a space id as its first argument and **no unscoped alternative exists to call**. The space id comes from the session, never from the request. Session middleware rejects before any handler runs. | Architecture Shaping Q2, and the decision the whole PRD turns on. Per-endpoint checks make `SEC01` depend on nobody ever forgetting; a store that cannot be called unscoped fails loudly instead of leaking silently. `SEC01`'s failure mode is silent, cross-company, and unrecoverable after the fact, so isolation must be structural rather than a matter of discipline. |
| 2026-08-04 | **The data store is SQLite**, a single file with no server process. | Architecture Shaping Q3. Three businesses recording roughly 200 entries a day is nowhere near a constraint; one file is trivially backed up and needs nothing running. **This supersedes the MongoDB forward-looking note of 2026-07-28**, which was recorded as context and never as a requirement. A document store buys nothing here and adds a server to operate before there is a user. |
| 2026-08-04 | **Sessions use a signed HTTP-only cookie with a server-side session table.** | Architecture Shaping Q4. `SEC04` requires sign-out and expiry to invalidate server-side. A stateless token cannot do that without a revocation list, which is a session table with extra steps. |
| 2026-08-04 | **`frontend/` and `backend/` share an origin in both environments**: Vite dev proxy in development, backend serves the built frontend in production. | Architecture Shaping Q5. Removes CORS, preflight, and cookie `SameSite` handling entirely, and leaves one process to run in production. |
| 2026-08-04 | **Deployment remains undecided**, deliberately. | Architecture Shaping Q6. `PRD-002` places deployment after backend beads exist and are built. Deciding hosting now would settle a question no built thing yet depends on, and would make a cross-space leak reachable by strangers rather than by a test. |
| 2026-08-04 | **The `PRD-001-UX01` paper-speed comparison will not be measured.** The acceptance oracle rests on the automated keyboard and focus checks alone. | Decided by the builder. `UX01`'s mechanical preconditions — keyboard-only entry, focus returning to the SKU field, fields clearing, no `tabindex` override — are what an automated check can hold, and they pass. Whether the app actually beats handwriting is a question about a person in a shop, better answered by the packet's "watch them use it" plan than by a stopwatch. **Accepted consequence:** the adoption bar named in `UX01` stays unproven, and `PRODUCT.md`'s stop signal *"says it is not faster than their sheet"* has no measurement behind it. **The window also closes:** `PRD-002` adds a network round trip to every entry, so a local baseline becomes unrecoverable afterwards. This was raised before the decision and accepted. |
| 2026-08-03 | **A login is the isolation boundary, and nothing more** (BQ-5). A username and passcode grant access to exactly one isolated data space. There is no entity above the login and no structure inside it. | Narrowed by the builder on 2026-08-03 from the earlier account-per-business framing. **Explicitly ruled out:** user profiles, roles, permissions, an admin layer, password reset, forgotten-login recovery, multiple users per login, and any business or team grouping above the login. Each login is its own space, full stop. This removes account management from scope; it does **not** reduce the isolation requirement, which is identical either way. |
| 2026-08-03 | **A lost passcode means permanently lost server data.** No reset, no recovery, no operator override. | Accepted consequence of the BQ-5 narrowing, recorded rather than left implicit. Nobody — including Snap Camp as operator — can restore access. **Partial mitigation:** the `.xlsx` export is the durable record, so any day already exported survives, but only if the business exports regularly, which `PRD-001` never made habit-forming. Revisit if a real user is locked out. |
| 2026-08-03 | **The backend stays its own PRD** (BQ-8), rescoped and renamed from "Multi-Tenant Backend" to isolated logins with server-side storage. It is not folded into `PRD-001` or reduced to a bead. | `PRD-PROTOCOL.md` requires a PRD shard before coding, and `DECOMPOSITION-PROTOCOL.md` lists missing PRD approval under Not A Bead Yet, so a bead is not structurally available. It cannot extend `PRD-001`, which is complete, approved, and browser-only by decision with `SEC02` and `SEC03` as tested requirements. Architecture Shaping triggers on auth, data models, APIs, external services, dependencies, and deployment — all six — and runs only on an approved PRD. Minimal login plus server storage still introduces a server, a persistent store, credentials, sessions, hosting, and secrets, none of which v1 has. |
| 2026-08-03 | **Snap Camp is deployed as one shared product serving multiple small businesses**, not one isolated instance per business. Each company's data must be inaccessible to every other company on the same deployment. | Confirmed by the builder, who is also the client, on 2026-08-03. Nothing in the repository had recorded a deployment model before this; `PROJECT-CONTEXT.md` said only "Deployment target: none configured". **Note:** `PRODUCT.md`'s "one product, one anchor, two witnesses — do not build three variants" is about not building three *different products* and was never evidence about deployment topology. |
| 2026-08-03 | **`PRD-001-SEC02` (no authentication or accounts) is reopened for `PRD-002` scope only.** It remains in force for v1 and is unchanged there. | `SEC02` was not made under a single-tenant assumption; it was made under a **no-deployment** assumption. In v1, isolation is not a feature — data never leaves the user's browser, so no mechanism exists for one company to reach another's. A shared deployment removes that property, and isolation must then be built and tested. Authorization is therefore not an addition to `SEC02` but the replacement for something being given up. **`SEC03` (no external network) is reopened on the same basis.** Both remain tested requirements of v1. |

| 2026-07-28 | The **Daily Inventory Recorder** is the canonical v1 scope. The Flexible Inventory Tracker is superseded. | Prototyping showed the dominant value is automatically producing the daily summary, not disambiguating near-identical items. |
| 2026-07-28 | The existing prototype is **design/source evidence only**. Its code is not reused, not preserved, not implementation authority, and not PRD, bead, review, transition, or acceptance approval. | Keeps the prototype as learning evidence without letting unreviewed code become the product. |
| 2026-07-28 | Build v1 for the anchor partner (needlepoint retail). The two witnesses confirm it generalizes. Do not build three variants. | Three industries is a focus trap; the anchor's pain is quantified and specific. |
| 2026-07-28 | SKU transformation and combo/bundle (kit) items are deferred to v2. | Both break the simple SKU model. Witness B gets real value from v1 with combos deferred, at zero cost to v1 scope. |
| 2026-07-28 | Design-partner identities are redacted to roles in this repository: anchor partner (needlepoint retail), witness A (lock manufacturing), witness B (coffee-paper logistics). No real customer names or supplier pricing are stored here. | The source packet sets this rule twice. This repository is committed and pushed. |
| 2026-07-28 | v1 has no authentication, no accounts, no personal data, and no external service calls. | Keeps sensitive surfaces at zero for the first slice. |
